# 079 — Narrated screencasts of tweet threads

Date: 2026-11-10

## Problem

The installation thread (`marketing/docs/tweets/001-installations`, posted as https://x.com/fastapistartkit/status/2118793752303305208) should also exist as a narrated video. The video should not show the tweets. It should take the thread as its script and demonstrate each point for real in VS Code, with the editor settings and fonts already used in `marketing/vscode-recordings`, the GitHub Dark theme, and the same narration voice.

The posted thread is the source of truth, and it differs from the local drafts. It has seven tweets instead of ten, with no installer, `Router` or AI agents tweets, and it drops three emojis.

`marketing/vscode-recordings` and `docs/videos` belong to an ongoing course recording, and they are recorded concurrently from `/tmp/issue-tracker` on port 8000.

## Alternatives

- **Remotion tweet cards** that show each posted tweet and its image. This was built first and rejected: it shows the tweets instead of teaching what they say.
- **Reusing the promo video's hand-built code scenes.** The scenes are animations, not a real editor, and they don't use the agreed VS Code look.
- **Adding takes to `marketing/vscode-recordings`.** Its workspace is pinned to issue-tracker tags, and it runs concurrently with the course recording, so the two would fight over `/tmp/issue-tracker`, the VS Code server data and port 8000.
- **A sibling recorder for tweet threads** that adapts the vscode-recordings pipeline to a project built from `uvx fastapi-startkit@latest init`.

## Decision

Use the last option. `marketing/docs/tweets/recorder/` holds adapted copies of `studio.py`, `record.py`, `workspace.py` and `narrate.py`, together with `vscode-settings.json` (the agreed settings, with `workbench.colorTheme` set to `GitHub Dark Default`), `voice.json` (`gemini-3.8-flash-tts`, `Charon`, same style) and `shell/.zshrc`.

- **Workspace.** It lives at `/tmp/startkit-demo`, so no home path appears in the prompt, the terminal or the pytest rootdir. Each take resets it to a cached `uvx fastapi-startkit@latest init` web template, keeping `.venv` and `node_modules`. It then replays the earlier steps through `prepare` functions (stages), so each take starts from exactly the state the previous take left. Frontend files are adopted from a cached `--frontend react` template, so every file shown is generated by the published installer.
- **Isolation.** The recorder uses its own `.vscode-server` (with the GitHub theme extension), its own `raw/` folder, the app on port 8100 and Vite on port 5199.
- **Timing.** Narration is voiced before recording. `narrate.py voice` writes each beat as `narration/<take>-<cue>.wav` plus a `.json` file with its length. During a take, `Studio.cue(name)` marks a beat and `Studio.hold(name)` waits until that beat's clip has finished, so the takes pace themselves to the voice without hand-tuned waits.
- **Thread folder.** `001-installations/video/` holds `thread.json` (the posted tweets, fetched via `api.fxtwitter.com/2/conversation/<id>` and checked against the syndication API's `conversation_count`), `episode.json` (beats per take, written from the posted tweets), `takes.py`, `narration/` and `recordings/`. The final film is `001-installations/001-installations.mp4`.

The nine takes follow the thread's seven tweets: intro, providers, logging, database, posts, testing, frontend, hot-reload and install.

## Implementation

- `uv run --script recorder/narrate.py <thread>/video voice` voices the beats, and it retries on 429, 500 and 503.
- `uv run --script recorder/record.py <thread>/video [take ...]` records the takes to `recordings/<take>.mp4`, with `.cues.json` files and still frames for preview.
- `uv run --script recorder/narrate.py <thread>/video` lays each beat at its cue, pads the video to fit, joins the takes and prints the `ffprobe` streams.
- `recorder/.gitignore` excludes `.vscode-server/`, `raw/` and `cache/`.

## Validation

- Every staged state is built and passes `uv run pytest` before recording. Takes that change code run `uv run pytest -q` after recording as a `verify` step.
- Still frames of each take are reviewed as a preview before the final render.
- `ffprobe` shows an h264 1920x1080 stream and an AAC audio stream for the full duration.
