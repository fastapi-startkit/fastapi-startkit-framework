# 079 — Narrated screencasts of tweet threads

Date: 2026-11-10 (revised 2026-11-11 to match the build reviewed on PR #370)

## Problem

The installation thread (`marketing/docs/tweets/001-installations`, posted as https://x.com/fastapistartkit/status/2118793752303305208) should also exist as a narrated video. The video should not show the tweets. It should take the thread as its script and demonstrate each point for real in VS Code, with the editor settings and fonts already used in `marketing/vscode-recordings`, the GitHub Dark theme, and the same narration voice.

The posted thread is the source of truth, and it differs from the local drafts. It has seven tweets instead of ten, with no installer, `Router` or AI agents tweets, and it drops three emojis.

`marketing/vscode-recordings` and `docs/videos` belong to an ongoing course recording, and they are recorded concurrently from `/tmp/issue-tracker` on port 8000.

## Alternatives

- **Remotion tweet cards** that show each posted tweet and its image. This was built first and rejected: it shows the tweets instead of teaching what they say. Remotion survives only as the compositor for the recorded takes (see below).
- **Reusing the promo video's hand-built code scenes.** The scenes are animations, not a real editor, and they don't use the agreed VS Code look.
- **Adding takes to `marketing/vscode-recordings`.** Its workspace is pinned to issue-tracker tags, and it runs concurrently with the course recording, so the two would fight over `/tmp/issue-tracker`, the VS Code server data and port 8000.
- **A sibling recorder for tweet threads** that adapts the vscode-recordings pipeline to a project built from `uvx fastapi-startkit init`.
- **Joining takes and narration with ffmpeg only** (`narrate.py` default step). It works, but every timing change needs a full re-encode to review. A Remotion composition lets the user scrub and preview the narrated cut live before anything is rendered.

## Decision

Use the sibling recorder, and compose the final cut in Remotion.

`marketing/docs/tweets/recorder/` holds adapted copies of `studio.py`, `record.py`, `workspace.py` and `narrate.py`, together with `vscode-settings.json` (the agreed settings, with `workbench.colorTheme` set to `GitHub Dark Default`), `voice.json` (`gemini-3.8-flash-tts`, voice `Charon`, same style) and `shell/.zshrc`.

- **Workspace.** It lives at `/tmp/startkit-demo`, so no home path appears in the prompt, the terminal or the pytest rootdir. Each take resets it to a cached `uvx fastapi-startkit==0.75.2 init` web template (cached under `recorder/cache/<pinned spec>/`, so a version bump regenerates it), keeping `.venv` and `node_modules`. It then replays the earlier steps through `prepare` functions (stages), so each take starts from exactly the state the previous take left. Frontend files are adopted from a cached `--frontend react` template, so every file shown is generated by the published installer. The install take still types `uvx fastapi-startkit@latest init my-app` on camera, because that is the command the thread tells readers to run.
- **Isolation.** The recorder uses its own `.vscode-server` (with the GitHub theme extension), its own `raw/` folder, the app on port 8100 and Vite on port 5199.
- **Voice.** `narrate.py` voices through OpenRouter (`google/gemini-3.8-flash-tts`, voice `Charon`, style sent as `instructions`) when `OPEN_ROUTER_KEY` is set, and falls back to the Gemini API directly when only `GEMINI_API_KEY` is set. Keys come from the environment first, then from `marketing/.env` (`MARKETING_ENV`), which is where the marketing tooling keeps its untracked secrets. A git worktree has no copy of that untracked file, so runs from a worktree export the key into the environment. The key is only required when a beat's `.wav` is missing or its `.txt` sidecar no longer matches the script; `timeline`, `takes` and `render` run keyless when every clip is cached.
- **Timing.** Narration is voiced before recording. `narrate.py voice` writes each beat as `narration/<take>-<cue>.wav` plus a `.json` file with its length. During a take, `Studio.cue(name)` marks a beat and `Studio.hold(name)` waits until that beat's clip has finished, so the takes pace themselves to the voice without hand-tuned waits.
- **Editor navigation.** Files and lines are reached through VS Code quick-open (`Ctrl/Cmd+P`, then a name or `:<line>`). `Studio.quick_open()` waits for the quick-input widget to appear, types, presses Enter and waits for the widget to close. If it is still open (the file index has not caught up, or nothing matched), it presses Escape and retries, up to five times, then raises. Before this, a fixed 0.6s sleep let typing land in the search box when quick-open was slow. `search.useIgnoreFiles` is off in `vscode-settings.json`, because the starter's `.gitignore` hides `.env.*` and quick-open could never find `.env.testing`. `Studio.until()` raises on timeout instead of carrying on, so a take that misses its condition fails rather than being recorded.
- **Composition.** `narrate.py <video> timeline` levels every clip into `narration/leveled/` (volumedetect mean to -19 dB, with a 0.84 sample-peak limiter) and writes `timeline.json`: per take, the recording, a lead, the recorded seconds, a hold and each beat's start time. Beats are placed at their cue plus offset, never closer than 0.15s to the previous beat. The lead is 0.4s, and the hold extends the take until 1.0s after its last beat ends. `marketing/docs/tweets/remotion/` is a Remotion 4.0.533 project (exact versions, `package-lock.json` committed, Node >= 20.11 for `import.meta.dirname`). Its `NarratedVideo` composition reads `timeline.json` through `calculateMetadata`. For each take, it freezes frame 0 for the lead, plays the muted recording, freezes the last frame for the hold, and places each leveled clip at its beat. `npm run preview <video dir>` opens Remotion Studio with the video folder as the public dir. `npm run render <video dir>` writes `<video dir>/<thread>.mp4` (h264 + AAC).
- **Thread folder.** `001-installations/video/` holds `thread.json` (the posted tweets, fetched via `api.fxtwitter.com/2/conversation/<id>` and checked against the syndication API's `conversation_count`), `episode.json` (beats per take, written from the posted tweets), `takes.py`, `narration/`, `recordings/` and `timeline.json`. The final film is `001-installations/video/001-installations.mp4`. It is rendered locally and never committed (`*.mp4`, `narration/*.wav` and `narration/leveled/` are ignored).

The nine takes follow the thread's seven tweets: intro, providers, logging, database, posts, testing, frontend, hot-reload and install. After the user's feedback, the intro opens on a hand-wired plain FastAPI `main.py`. The providers take only shows the fresh app's provider list (logging and FastAPI), with no code typed. Adding the database provider is left to the database take's `artisan db:install`.

## Implementation

From `marketing/docs/tweets/recorder`:

- `uv run --script narrate.py <thread>/video voice` voices missing or changed beats, and retries on 429, 500, 502 and 503 (honouring `retry-after`, otherwise exponential backoff capped at 60s).
- `uv run --script record.py <thread>/video [take ...]` records the takes to `recordings/<take>.mp4`, with `.cues.json` files and still frames for preview.
- `uv run --script narrate.py <thread>/video timeline` writes the leveled clips and `timeline.json`.
- `recorder/.gitignore` excludes `.vscode-server/`, `raw/` and `cache/`.

From `marketing/docs/tweets/remotion`:

- `npm run preview ../<thread>/video` opens the narrated cut in Remotion Studio.
- `npm run render ../<thread>/video` renders `<thread>/video/<thread>.mp4`.

The older ffmpeg path (`narrate.py <thread>/video`, default step `render`) still joins the takes into `<thread>/<thread>.mp4`. It is kept as a fallback and is not the source of the approved cut.

## Validation

- Every staged state is built and passes `uv run pytest` before recording. Takes that change code run `uv run pytest -q` after recording as a `verify` step.
- Still frames of each take, and then the full narrated cut in Remotion Studio, were reviewed by the user. The user approved the 4:20 cut on 2026-11-11.
- `ffprobe` of the render shows h264 1920x1080 at 30fps and AAC 48 kHz stereo for 259.8s. The render measures -18.5 LUFS integrated and -4.4 dBTP true peak.

## Known issues held for the user's decision

The PR #370 review measured four issues in the approved cut. They are recorded here rather than fixed, because each fix needs a re-record or a re-render of the approved cut.

- The quick-open and go-to-line boxes are visible in about 29 short windows.
- The install take opens on the VS Code Welcome page, behind the command palette (around 232.6s).
- Twelve silences run longer than 2.7s. The longest three (20.7s, 16.3s and 11.8s) sit under on-camera typing and the server start plus `curl`, not under installer progress.
- There is no final `loudnorm` pass, so true peak is -4.4 dBTP against a -1.4 dBTP ceiling, and the output is stereo while the leveled clips are mono.
